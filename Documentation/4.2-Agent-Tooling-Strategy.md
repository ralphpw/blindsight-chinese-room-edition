## The Core Problem: Why Fresh Sessions Matter

### The Quality Imperative

Literary translation demands **absolute voice consistency** across all 22 chapters. Unlike technical documentation where minor variations are acceptable, Peter Watts' distinctive style—with its predator/prey metaphors, clinical precision, and Sarasti's kayfabe—must remain consistent from Chapter 1 to Chapter 22.

**A single contaminated LLM session destroys this consistency.**

### What Happens Without Fresh Sessions

When LLMs maintain long conversation threads, accumulated context degrades quality in measurable ways:

| Contamination Type | Cause | Effect | Example |
|-------------------|-------|--------|---------|
| **Context Pollution** | Previous chapters bleed into new ones | Inconsistent voice across chapters | Ch. 1 uses predator metaphors, Ch. 15 shifts to generic descriptions |
| **Model Drift** | Accumulated corrections shift behavior | Overcorrections in later chapters | Feedback "less flowery" in Ch. 5 strips ALL metaphors from Ch. 6 |
| **Token Exhaustion** | Context window fills up | Automatic summarization triggered | Character voice matrices collapse to "analytical, detached" |

### Concrete Example

```
Chapter 1 (Fresh Session - 0K context accumulated):
"Her eyes tracked me with the calculating patience of a spider sensing vibrations."
✓ Maintains Watts' predator/prey metaphor framework
✓ Visceral, precise, characteristic

Chapter 2 (Same Session - 80K context accumulated):
"She watched me carefully, thinking through her response."
✗ Generic, safe description
✗ Lost Watts' distinctive intensity
✗ Model defaulting to training patterns (fatigue drift)
```

**The problem:** The LLM unconsciously "plays it safe" as context accumulates, gradually shifting toward generic prose that's easier to generate but loses the author's voice.

## Three Types of Quality Degradation

### 1. The "Summarizing Conversation" Catastrophe

**When it happens:** Context window reaches ~70-80% capacity

**What you see:**
```
User: [Chapter 15 translation request with full context]
LLM: "I notice our conversation is getting quite long. 
      Let me summarize what we've covered so far..."
```

**Why it's catastrophic:**

| What Gets Lost | Original Context | After Summarization |
|----------------|------------------|---------------------|
| **Character Voices** | "Siri Keeton: Voice constructed through absence. Gaps in social cognition manifest as clinical precision. Emotional vocabulary acquired academically, deployed incorrectly - like a dictionary user who knows definitions but not connotations. Metaphors chosen for accuracy, not resonance." | "Siri: Analytical, emotionally detached." |
| **Metaphor Frameworks** | "Sarasti's kayfabe: Predator/prey dynamics as existential performance. Every interaction is threat display or submission test." | "Sarasti uses predator metaphors." |
| **Legal Requirements** | "Fair use allows phrase-level borrowing but NOT paragraph-level copying. Check each Sarasti line against source." | "Follow fair use guidelines." |

**Recovery:** Impossible. Cannot reload 50K+ tokens of lost nuance without re-exceeding window.

**Prevention:** Mandatory. Detection protocol in every API call:

```python
DETECTION_PROMPT = """
CRITICAL PRE-FLIGHT CHECK:
1. Is this a fresh conversation with no prior history?
2. Can you see COMPLETE Character-Voice-Reference.md (15K+ tokens)?
3. Can you see COMPLETE Legal-Requirements.md (8K+ tokens)?
4. Do you have the FULL source chapter (not summarized)?

If ANY answer is "No": RESPOND ONLY "ABORT: Summarization detected"
"""

# LLMs CAN detect this and will abort
if "ABORT:" in response[:500]:
    raise SummarizationError("Context compromised - restart required")
```

### 2. Sequential Bleeding (Cross-Chapter Contamination)

**What happens:** Early chapters' translation choices unconsciously bias later chapters

**Example:**
```
Chapter 3: "幽灵肢体综合症" → "phantom limb syndrome"
[Term added to LLM's working vocabulary]

Chapter 8: "幽灵肢体综合症" encountered again
[LLM auto-reuses Chapter 3 translation without reconsidering]

Problem: Chapter 8 is Szpindel's POV (clinical) vs. Chapter 3's Keeton POV (philosophical)
Better translation: "residual limb sensation" (more technical)
```

**Why fresh sessions prevent this:** Each chapter reconsiders terminology from scratch, choosing context-appropriate translations.

### 3. Correction Accumulation (Behavioral Drift)

**What happens:** Human feedback in one chapter shifts LLM behavior in unintended ways

**Example:**
```
Chapter 5 Feedback: "Less flowery - Watts doesn't romanticize the science"
[LLM adjusts internal parameters]

Chapter 6 Translation:
[LLM OVERCORRECTS, stripping ALL metaphorical language]

Problem: Chapter 6 is Cunningham's POV where vivid metaphor IS appropriate
```

**Why fresh sessions prevent this:** No accumulated corrections to bias later chapters. Each starts neutral.

### The Solution: Fresh Session Per Chapter

| Benefit | How It Works |
|---------|-------------|
| **Clean slate** | No translation decisions from previous chapters |
| **Full token budget** | All 200K tokens available for THIS chapter |
| **Unbiased interpretation** | Style guidelines applied fresh, not filtered through corrections |
| **Maximum creativity** | Model hasn't settled into "safe" patterns |
| **Predictable costs** | Every chapter uses ~55K tokens (27% of limit) |

## Table-Driven Execution Strategy

### The KANBAN as Source of Truth

All translation work is driven by **Tasks/KANBAN.md** - a single table that defines what to execute, how to execute it, and tracks progress automatically.

**Execution Flow:**

```
Tasks/KANBAN.md (defines ticket metadata)
    ↓
Instructions/Tickets/T018.md (defines context requirements)
    ↓
MCP Server loads specified context
    ↓
Fresh API session executes translation
    ↓
Output saved + KANBAN auto-updated
```

### KANBAN Table Structure

```markdown
| ID | Task | Status | LLM | Limit | Req'd | Cost | Owner | Started | Done |
|----|------|--------|-----|-------|-------|------|-------|---------|------|
| T018 | Translate Chapter 1 | ⏳ TODO | Opus 4.1 | 200K | 55K | $15 | - | - | - |
```

**What the MCP server reads:**
- **Ticket ID:** T018
- **LLM:** claude-opus-4.1 (determines which API to call)
- **Token Limit:** 200K (safety threshold)
- **Expected Usage:** 55K (for validation)
- **Status:** ⏳ TODO (determines if should execute)

### Ticket File Structure

```markdown
# Instructions/Tickets/T018-Translate-Chapter-01.md

## Context Requirements

**Required Reading:**
- Instructions/Character-Voice-Reference.md (15K tokens)
- Instructions/Using-Watts-Language-Legal-Requirements.md (8K tokens)
- Source/chapter_01.txt (25K tokens)

**Token Budget:** ~48K total (24% of 200K limit) ✓ SAFE

## Instructions
[Translation prompt goes here...]
```

**What the MCP server does:**
1. Loads ONLY the files listed in "Required Reading"
2. Verifies total tokens < 50% of limit (prevents summarization)
3. Creates fresh API client
4. Executes with summarization detection
5. Saves output to `Output/chapter_01.md`
6. Updates KANBAN: `✅ DONE | 2025-11-12 | 49,234 tokens`

### Benefits of Table-Driven Approach

| Benefit | How It Works | Example |
|---------|-------------|---------|
| **No hardcoded logic** | Change KANBAN, behavior changes | Switch T027 from Opus to Sonnet → MCP uses different API |
| **Single source of truth** | KANBAN shows what's needed | Look at KANBAN to see all 22 chapters at a glance |
| **Easy restarts** | Mark completed tickets as DONE | Stage 3 fails at Ch. 15? Mark T018-T032 DONE, continue from T033 |
| **Human override** | Edit KANBAN to change strategy | Re-do Ch. 10 with different LLM mid-project |
| **Audit trail** | KANBAN records completion time, tokens used | Track actual vs. estimated costs |
| **Progress visibility** | Watch KANBAN update in real-time | See status change from TODO → DONE as MCP executes |

### Example: Mid-Project Strategy Change

**Scenario:** Chapter 10's quality is poor, want to retry with Sonnet 4.0

**Action:** Edit KANBAN:
```markdown
| T027 | Translate Chapter 10 | ❌ REDO | Sonnet 4.0 | 200K | 55K | $8 | - | - | - |
```

**MCP Server automatically:**
- Uses `claude-sonnet-4.0` instead of `claude-opus-4.1`
- Loads fresh session (no memory of previous failed attempt)
- Re-translates Chapter 10
- Updates KANBAN when complete

**No code changes. No manual intervention. Table drives everything.**

## Implementation Approaches

### Approach 1: MCP Server for GitHub Copilot (RECOMMENDED)

**Why this is ideal for this project:**
- Stay in GitHub Copilot (no context switch)
- Table-driven execution (KANBAN → MCP → API)
- Fresh sessions guaranteed (MCP spawns new clients per ticket)
- KANBAN writeback (auto-updates progress)
- Human oversight (watch execution in Copilot chat, intervene anytime)

**Architecture:**

```
┌─────────────────────────────┐
│ VS Code (Single Instance)   │
│                             │
│ ┌─────────────────────────┐ │
│ │ GitHub Copilot Chat     │ │
│ │                         │ │
│ │ > @ticket-executor      │ │
│ │   execute_stage 3       │─┼──┐
│ │                         │ │  │
│ │ [Progress updates...]   │◄┼──┘
│ └─────────────────────────┘ │
│                             │
│ ┌─────────────────────────┐ │
│ │ KANBAN.md (live updates)│ │
│ └─────────────────────────┘ │
└─────────────────────────────┘
        │
        │ MCP Protocol
        ▼
┌─────────────────────────────┐
│ MCP Server (background)     │
│                             │
│ execute_ticket(T018):       │
│  1. Parse KANBAN for T018   │
│  2. Load ticket file        │
│  3. Load context files      │
│  4. Verify token budget     │
│  5. Create fresh API client │
│  6. Execute with detection  │
│  7. Save output             │
│  8. Update KANBAN           │
│  9. Destroy client          │
└─────────────────────────────┘
        │
        ▼
┌─────────────────────────────┐
│ Anthropic/OpenAI/etc APIs   │
│ (Each call = fresh session) │
└─────────────────────────────┘
```

**Usage in GitHub Copilot Chat:**

```typescript
// Execute single ticket
@ticket-executor execute_ticket ticket_id="T018"

// Execute entire stage (loops through all tickets)
@ticket-executor execute_stage stage=3

// Manual KANBAN update (if needed)
@ticket-executor update_kanban ticket_id="T018" status="✅ DONE"

// Generate failure report
@ticket-executor abort ticket_id="T018" reason="Token budget exceeded"
```

**MCP Server Core Logic:**

```typescript
server.setRequestHandler("tools/call", async (request) => {
  if (request.params.name === "execute_ticket") {
    const { ticket_id } = request.params.arguments;
    
    // Read KANBAN to get ticket metadata
    const kanban = await parseKanban("Tasks/KANBAN.md");
    const ticketMeta = kanban.findById(ticket_id);
    
    // Load ticket file for context requirements
    const ticketFile = await loadTicket(`Instructions/Tickets/${ticket_id}.md`);
    
    // Load ONLY the context files specified in ticket
    const context = await loadFiles(ticketFile.context_requirements.required);
    
    // Pre-flight token verification
    const tokens = await countTokens(context);
    if (tokens > ticketMeta.token_limit * 0.5) {
      return await generateFailureReport(ticket_id, "Token budget exceeded");
    }
    
    // Create FRESH API client (new session)
    const client = createClient(ticketMeta.llm); // "Opus 4.1" → new Anthropic()
    
    // Execute with summarization detection
    const result = await executeWithDetection(client, ticketFile, context);
    
    // Save output file
    await writeOutput(`Output/${ticket_id}.md`, result.output);
    
    // Update KANBAN table
    await updateKanban(ticket_id, {
      status: "✅ DONE",
      completed: new Date().toISOString(),
      actual_tokens: result.usage.total_tokens
    });
    
    return { 
      success: true,
      tokens: result.usage.total_tokens,
      cost: calculateCost(result.usage, ticketMeta.llm)
    };
  }
  
  if (request.params.name === "execute_stage") {
    const { stage } = request.params.arguments;
    const tickets = await getStageTickets(stage); // e.g., T018-T039 for Stage 3
    
    for (const ticket_id of tickets) {
      try {
        await execute_ticket({ ticket_id }); // Fresh session per ticket
      } catch (error) {
        await generateFailureReport(ticket_id, error.message);
        const shouldContinue = await askUser("Continue to next ticket?");
        if (!shouldContinue) break;
      }
    }
  }
});
```

**Advantages:**
- ✅ Stays in familiar GitHub Copilot environment
- ✅ Fresh sessions per ticket (guaranteed isolation)
- ✅ Table-driven (edit KANBAN, not code)
- ✅ KANBAN auto-updates (live progress tracking)
- ✅ Human oversight (watch in chat, intervene anytime)
- ✅ Looping automation (`execute_stage` handles 22 chapters)
- ✅ LLM selection per ticket (Opus for translation, Sonnet for reviews)
- ✅ Abort + failure reports (automatic error handling)

**Disadvantages:**
- Requires MCP server development (~4-6 hours)
- Need API keys configured
- Initial setup complexity

### Approach 2: Direct API Scripts (Fully Automated)

**Best for:** Unattended batch processing

**Implementation:**

```python
# scripts/run_stage3.py
import anthropic

def execute_ticket(ticket_id: str):
    # Parse KANBAN for metadata
    ticket_meta = parse_kanban_row(ticket_id)
    
    # Load ticket file
    ticket = load_ticket(f"Instructions/Tickets/{ticket_id}.md")
    
    # Load context (ONLY what ticket specifies)
    context = load_files(ticket.context_requirements.required)
    
    # Verify token budget
    assert count_tokens(context) < ticket_meta.token_limit * 0.5
    
    # Create FRESH client
    client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
    
    # Execute
    response = client.messages.create(
        model=ticket_meta.llm_model,
        max_tokens=8000,
        messages=[{
            "role": "user",
            "content": f"{DETECTION_PROMPT}\n\n{context}\n\n{ticket.instructions}"
        }]
    )
    
    # Check for abort
    if "ABORT:" in response.content[0].text[:500]:
        raise SummarizationError()
    
    # Save + update KANBAN
    save_output(ticket_id, response.content[0].text)
    update_kanban(ticket_id, "✅ DONE", response.usage.total_tokens)

# Run all 22 chapters
for chapter in range(1, 23):
    ticket_id = f"T{17+chapter:03d}"  # T018-T039
    execute_ticket(ticket_id)
```

**Advantages:**
- Fully automated (no human intervention)
- Cheapest ($330 for 22 chapters)
- Reproducible (same inputs → same outputs)

**Disadvantages:**
- No human oversight
- Can't intervene mid-execution
- Must handle errors programmatically

## Context Control Patterns

### Dynamic Context Loading (Table-Driven)

**Key insight:** Different tickets need different context. The MCP server loads ONLY what each ticket specifies.

| Ticket | Context Files | Tokens | Why |
|--------|--------------|--------|-----|
| **T013** (Jargon Extraction) | `Source/chapter_01.txt` | 25K | Just identify terms, no interpretation needed |
| **T018** (Chapter Translation) | `Character-Voice-Reference.md`<br>`Legal-Requirements.md`<br>`Source/chapter_01.txt` | 48K | Standard translation context |
| **T062** (Style Analysis) | `Character-Voice-Reference.md`<br>`Legal-Requirements.md`<br>`Literary-Style-Analysis-Template.md`<br>`Character-Philosophy.md`<br>`Source/chapter_01-03.txt` | 120K | Deep analysis needs full framework |
| **T041** (Consistency Review) | `Consistency-Review-Guidelines.md`<br>`Output/chapter_01-22.md` | 150K | Needs entire manuscript |

### Context Loading Priority

If token budget forces cuts, remove in this order:

1. **Keep:** Character voices (cannot translate without)
2. **Keep:** Legal requirements (prevents copyright violations)
3. **Keep:** Source text (the actual content)
4. **Drop:** Style guidelines (nice-to-have, but not critical)
5. **Drop:** Examples (can infer from guidelines)

### Pre-Flight Validation

```python
def validate_context_budget(ticket_id: str) -> bool:
    ticket = load_ticket(ticket_id)
    context = load_files(ticket.context_requirements.required)
    tokens = count_tokens(context)
    limit = ticket.token_limit
    
    # Check against 50% threshold
    if tokens > limit * 0.5:
        print(f"⚠️  WARNING: {tokens:,} tokens ({tokens/limit:.1%} of limit)")
        print(f"   Risk of summarization - consider reducing context")
        return False
    
    print(f"✓ SAFE: {tokens:,} tokens ({tokens/limit:.1%} of limit)")
    return True
```

## Quality Metrics and Monitoring

### Real-Time Monitoring

Track these metrics as tickets execute to detect contamination early:

| Metric | Expected | Red Flag | Action |
|--------|----------|----------|--------|
| **Token Usage** | ~55K ± 5K per chapter | Chapter uses >70K | Review for verbosity/meta-commentary |
| **Translation Time** | 30-45 min per chapter (API) | Chapter takes >78 min | Possible context overload, check session |
| **Output Length** | Consistent across chapters | Variance >30% | Either chapter length differs OR quality issue |
| **Vocabulary** | Context-appropriate per chapter | Same term 3+ different ways | Either contamination OR appropriate variation |
| **Style Complexity** | avg_clause_depth ~2.3-2.5 | Sudden drop to <1.8 | Possible fatigue drift, re-translate |

### Automated Validation

```python
def validate_output(ticket_id: str, output: str) -> ValidationResult:
    """Run after each ticket completes"""
    
    # Catastrophic failure checks
    assert len(output) > 1000, "Output too short"
    assert "summarizing" not in output.lower()[:1000], "Hit summarization"
    assert "I notice" not in output[:200], "Meta-commentary detected"
    assert "ABORT:" not in output[:500], "LLM aborted - context compromised"
    
    # Token usage validation
    usage = get_token_usage(ticket_id)
    expected = get_expected_usage(ticket_id)
    if usage > expected * 1.5:
        log_warning(f"{ticket_id}: High token usage ({usage} vs {expected} expected)")
    
    # Contamination check (compare to previous chapter)
    if is_chapter_ticket(ticket_id):
        prev_output = get_previous_chapter_output(ticket_id)
        similarity = calculate_similarity(output, prev_output)
        if similarity > 0.4:
            log_warning(f"{ticket_id}: Suspiciously similar to previous chapter")
    
    return ValidationResult(passed=True, warnings=warnings)
```

### Red Flags Requiring Re-Translation

**Immediate abort:**
- "Summarizing conversation" appears anywhere
- "ABORT:" in first 500 chars of output
- Output <1000 chars (translation failed)
- Token usage >70K (context bloat or verbose output)

**Review required:**
- Output length variance >30% from average
- Vocabulary shifts (same source term translated 3+ inconsistent ways)
- Meta-commentary ("I notice...", "To maintain consistency...")
- Style complexity sudden drop (avg_clause_depth falls >0.5)

## Common Mistakes to Avoid

### Mistake 1: "I'll just tell the LLM to forget"

```
User: "Forget everything from the previous chapter and start fresh."
LLM: "Understood, I'll focus only on Chapter 2."
[Proceeds to use Chapter 1's translation decisions anyway]
```

**Why it fails:** LLMs cannot selectively erase context. Conversation history remains in context window.

**Solution:** Terminate session completely. Create new API client.

---

### Mistake 2: "I'll split chapters into scenes"

```
Session 1: Translate Chapter 5, Scene 1
Session 2: Translate Chapter 5, Scene 2  
Session 3: Translate Chapter 5, Scene 3
```

**Why it fails:** Voice consistency within chapter is lost. Scene transitions become jarring.

**Solution:** Translate entire chapter in one session (maintain internal coherence).

---

### Mistake 3: "I'll reuse the session for similar chapters"

```
Session 1: Chapter 1 (Keeton POV)
[Session continues]
Session 1: Chapter 3 (Keeton POV)  # Same narrator, why not?
```

**Why it fails:** Chapter 3's translation is biased by Chapter 1's choices, even with same narrator.

**Solution:** Fresh session per chapter, regardless of POV character.

---

### Mistake 4: "I'll load all 22 chapters for consistency"

```
Context: [All 22 chapter source texts + all instructions]
LLM: [Summarizing conversation message]
```

**Why it fails:** Instant token budget explosion (500K+ tokens). Guaranteed summarization trigger.

**Solution:** Load ONLY the chapter being translated. Consistency comes from shared guidelines, not shared context.

---

### Mistake 5: "I'll continue after an error"

```
Chapter 10: [Error occurs mid-translation]
User: "Continue from where you left off"
LLM: [Produces lower-quality second half]
```

**Why it fails:** Partial translations show quality degradation. Session is already compromised.

**Solution:** 
1. Terminate session immediately
2. Review error logs
3. Fix root cause (reduce token count, fix input files)
4. Start ENTIRELY NEW session
5. Re-translate ENTIRE chapter from beginning

## Conclusion

**The Rule:** One ticket, one session, one fresh start.

**Why it matters:**
- **Voice consistency:** No contamination between chapters
- **Predictable costs:** Every chapter uses ~55K tokens
- **Reproducibility:** Same inputs always produce same quality
- **Legal safety:** No cross-chapter copyright violations

**How it works:**
- KANBAN table defines execution
- Ticket files specify context requirements
- MCP server spawns fresh sessions
- Output auto-saved, KANBAN auto-updated

**Cost of compliance:** $15/chapter × 22 chapters = $330

**Cost of non-compliance:** Re-doing contaminated chapters (time + money) + degraded final quality

**Start fresh. Stay fresh. Finish clean.**
